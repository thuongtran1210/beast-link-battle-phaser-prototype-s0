## 1. Technical Direction
Recommended stack for P0:
- **Phaser + TypeScript** — browser gameplay prototype.
- **Vite** — fast local development/build.
- No backend for P0.
- Session metrics stay local in memory and are shown at the end of the run.
- One main gameplay scene with a small internal phase state machine instead of recreating Unity's full scene/service architecture.
The goal is **fast validation**, not architecture parity with Unity.

## 3. RuleConfig — One Place for Adopted Values
`RuleConfig.ts` is the only place where baseline tuning values should live.
Suggested structure:
```plain text
PUZ-001   boardSize = 6
MATCH-001 maxPathTurns = 2

COMBO-002 comboInitial = 5.0
COMBO-003 comboBonus = 0.3
COMBO-004 comboCap = 5.0

QUEUE-001 queuePerMatch = 1

STAR-001
star1Cost = 1
star2Cost = 3
star3Cost = 9

ENERGY-001 energyPerMatch = 10
ENERGY-002 energyMax = 20
```
Each value should keep its Rule ID in a comment or metadata field.
A Test Variant (biến thể thử nghiệm) must not overwrite the baseline silently.
Example:
```plain text
baseline.comboBonus = 0.3
variantA.comboBonus = 0.5
variantA.status = Experimental
```
## 4. Phase State Machine
P0 only needs four gameplay phases:
```plain text
Preparation
    ↓ Combo ends
Resolution
    ↓ Start Battle
Battle
    ↓ Enemy resolved
Result
    ↓ Next run / restart
Preparation
```
### Preparation
- Beast-only board.
- valid Beast match → +1 Queue.
- first valid match starts Combo.
- Combo expiration → Resolution.
### Resolution
- board input disabled.
- show current Beast Queue.
- allow individual deploy.
- allow Start Battle.
### Battle
- Energy-only board.
- simplified battle model active.
- Energy Match → gauge.
- full gauge → Skill Ready.
### Result
- stop gameplay systems.
- show Session Summary (tóm tắt phiên chơi).

## 6. Event Contracts (hợp đồng sự kiện)
Use a small event layer so gameplay systems remain readable without overengineering.
Recommended events:
- `match:valid`
- `match:invalid`
- `combo:started`
- `combo:updated`
- `combo:ended`
- `queue:changed`
- `unit:deployed`
- `phase:changed`
- `energy:changed`
- `energy:ready`
- `skill:cast`
- `session:ended`
Example chain:
```plain text
OnetMatcher
→ match:valid
→ ComboSystem
→ BattleQueue OR EnergySystem
→ SessionMetrics
→ UI refresh
```

## 9. Minimal Automated Checks
Before player testing, verify logic with small deterministic checks.
### OnetMatcher
- straight path valid.
- one-turn L valid.
- two-turn Z valid.
- outer-border U valid.
- path requiring \>2 turns invalid.
- blocked route invalid.
- different content invalid.
### STAR-001
- 0 queue → no unit.
- 1 → one 1★.
- 3 → one 2★.
- 9 → one 3★.
- 10 → one 3★ + one 1★ if bulk conversion consumes greedily from highest tier.
- individual and Start Battle paths return equivalent total conversion for the same queue.
### Energy
- 0 → match → 10.
- 10 → match → 20 Ready.
- Cast → 0.
These checks are for prototype reliability, not proof of good game balance.
## 10. Anti-Scope-Creep Rules (chống phình phạm vi)
Do not add a feature to P0 unless it directly supports one of the five first validation questions.
Specifically avoid:
- inventory UI,
- shop,
- multiple Pet systems,
- full enemy roles,
- fancy path animation,
- production-quality art,
- save/load,
- progression,
- multiple skill types before one skill works,
- architecture refactor before the full P0 loop is playable.
A placeholder rectangle with a clear state is better than a polished subsystem that does not help validation.
## 11. First Coding Order
Recommended first coding sequence:
**RuleConfig → BoardModel → BoardGenerator → OnetMatcher → BoardView → DeadlockResolver → ComboSystem → BattleQueue → PhaseController → ResolutionPanel → StarConverter → SimpleBattleModel → EnergySystem → SessionMetrics → SessionSummary**
The first checkpoint should be **S1**, not the full game.
## 12. Next Decision Gate
Before implementation begins, only two technical choices remain:
1. **Rendering approach:** simple Phaser shapes/text first, no art dependency.
2. **Battle representation:** numeric HP/power bars first, no unit AI.
Default for P0: choose both simple options.
Once those defaults are accepted, implementation can start without another design decision.
