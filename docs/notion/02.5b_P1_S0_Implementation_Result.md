## Objective
Migrate the Phaser state flow from the completed P0 structure:
```plain text
Preparation → Resolution → Battle + Energy Puzzle → Result
```
to the P1 state graph:
```plain text
BeastRush → EnergyRush → BattleSetup → Battle → Result
```
P1-S0 proves only the new state topology. It does not implement the full P1 mechanics yet.
## Reuse
Keep and reuse where possible:
- BoardModel
- BoardGenerator
- OnetMatcher
- DeadlockResolver
- BoardView
- ComboSystem
- BattleQueue
- StarConverter
- SessionSummary / Result shell
Do not refactor these systems unless the state migration requires a small compatibility change.
## Required Behavior
### BeastRush
- Beast-only 6×6 Onet board.
- Existing Beast matching still feeds BattleQueue.
- Existing Combo behavior may remain temporarily for S0.
- When the current Beast phase ends, transition to **EnergyRush**, not Resolution/BattleSetup.
### EnergyRush
- Create a fresh Energy-only 6×6 board.
- Reuse Onet + deadlock handling.
- Do not start active Battle yet.
- S0 does not require final EnergyQueue logic.
- Temporary Energy output may be a clearly labeled fixture if needed only to prove transition.
- For S0 only, use a validation-only **Continue to Battle Setup** action to leave EnergyRush. Label it **prototype-only navigation fixture**. Do not invent an Energy timer, quota, gauge threshold, or final EnergyQueue rule.
### BattleSetup
- No puzzle interaction.
- Show a minimal setup shell.
- Show current BeastQueue / converted unit summary if already available.
- Show a single **Start Battle** action.
- Do not implement formation/drag/drop yet.
- Start Battle → Battle.
### Battle
- No Energy puzzle board.
- No Energy matching.
- No new autonomous-combat design yet in S0.
- A minimal Battle shell is acceptable only to prove the state transition.
- Existing P0 battle fixture may be reused temporarily if it does not re-enable puzzle input.
- For S0 only, use a validation-only **Complete S0 Battle** action to reach Result. Label it **prototype-only navigation fixture**. Do not invent P1 combat timing or damage rules in this slice.
### Result / Restart
- Result continues to use the readable Session Summary shell.
- Restart returns to a fresh **BeastRush**, not old Preparation.
- All per-run state used by S0 must reset cleanly.
## State Naming
Prefer explicit P1 phase names in code and UI:
- BeastRush
- EnergyRush
- BattleSetup
- Battle
- Result
Avoid keeping a generic P0 name such as Resolution when the behavior now represents BattleSetup.
## Forbidden in S0
Do not implement:
- EnergyQueue final rules,
- exact Energy match → charge conversion,
- Beast role combat stats,
- battlefield slots / formation,
- drag-and-drop arrangement,
- autonomous enemy damage,
- Heal / Shield / timed skill redesign,
- multiple Energy skills,
- waves,
- meta systems,
- mid-combat reposition,
- balance tuning.
## Deterministic Checks
Add checks for:
1. initial phase = BeastRush,
2. BeastRush uses Beast-only content,
3. BeastRush end → EnergyRush,
4. EnergyRush uses Energy-only content,
5. EnergyRush end → BattleSetup,
6. BattleSetup rejects puzzle input,
7. Start Battle → Battle,
8. Battle has no active puzzle board/input,
9. Battle → Result works through the temporary S0 fixture,
10. Restart → fresh BeastRush,
11. BeastQueue/reset state does not leak across restart,
12. existing Onet / deadlock / STAR regression checks still pass where applicable.
## Visible UI Check
The header must make the state obvious:
- Current Phase: Beast Rush
- Current Phase: Energy Rush
- Current Phase: Battle Setup
- Current Phase: Battle
- Current Phase: Result
This is validation UI, not production polish.
## Verification
After implementation:

3. run `npm.cmd run build`,
4. live-browser verify:
	**BeastRush → EnergyRush → BattleSetup → Battle → Result → Restart → BeastRush**,
