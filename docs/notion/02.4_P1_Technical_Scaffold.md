# 02.4 — P1 Technical Scaffold — Dual Queue + Tactical Battle

> **Purpose:** technical plan for synchronizing the Phaser validation prototype to the adopted P1 design. This is not production architecture.
**Design Source:** <mention-page url="https://app.notion.com/p/3ec2674d32c3812296a8de866c65c434"/>
**Decision Record:** <mention-page url="https://app.notion.com/p/3ec2674d32c381e3bdb8fe9d409516f0"/>
**Current Phaser Matrix:** <mention-page url="https://app.notion.com/p/3ec2674d32c381919709d2b17efb3f57"/>
## P1 Target Flow
```plain text
Deck Setup / Test Fixture
    ↓
Beast Rush
    ↓
Energy Rush
    ↓
Battle Setup
    ↓
Auto Battle + Timed Energy Cast
    ↓
Result
    ↓
Restart / Next Cycle
```
P0 remains the verified historical baseline. P1 changes structure deliberately and must not silently overwrite P0 evidence.
## Scope Principle
The first P1 build should prove only three structural ideas:
1. **Dual pre-Battle queues:** Beast and Energy are both collected before combat.
2. **Beast arrangement:** army position/role matters before combat starts.
3. **Autonomous Battle + timed Energy:** Battle progresses without puzzle input; Energy is cast from stored charges.
Do not add waves, meta, progression, full Unity AI parity or production art.
## Proposed State Machine
```plain text
BeastRush
EnergyRush
BattleSetup
Battle
Result
```
P0 states may be renamed/refactored only as needed. Keep changes small and testable.
## Data Models
### BeastQueue
Reuse the existing content-specific queue concept.
```plain text
beastId
count
role
```
### EnergyQueue
New P1 concept.
```plain text
energyId
charges
skillType
```
A successful Energy match should add to stored pre-Battle Energy output. Exact conversion is a design parameter and must remain explicit.
### DeployedUnit
Extend the current record only enough to support arrangement.
```plain text
unitId
beastId
role
star
slot
hp
damage
range / attackProfile
```
### BattleSlot
Minimal spatial representation.
```plain text
slotId
row
column
occupantUnitId | null
```
## Beast Roles
P1 should expose the Unity-aligned role vocabulary:
- Tanker
- Assassin
- Ranger
- Mage
The first Phaser implementation does not need full Unity behavior. Each role needs one clearly readable combat difference so arrangement can be tested.
Example fixture only:
- Tanker: higher HP / front-line preference.
- Assassin: higher burst / fragile.
- Ranger: ranged sustained damage.
- Mage: support or Energy-related modifier.
These numbers are **prototype fixtures**, not adopted balance rules.
## Energy Skills
Do not recreate the P0 "match during Battle → fill gauge" loop.
For the first P1 slice:
- collect Energy before Battle,
- enter Battle with finite queued charges,
- Battle continues even if no skill is used,
- player chooses when to consume a charge.
Start with **one timing-sensitive skill** before adding multiple skills.
Recommended first fixture: **Heal** or **Shield**, because immediate cast at full HP is visibly wasteful and therefore creates timing value. Damage can remain a later comparison skill.
## Autonomous Battle Requirement
Battle must advance on its own.
Minimum model:
- Player units attack Enemy automatically.
- Enemy damages Player Army automatically.
- Battle time/ticks continue without user input.
- Enemy defeated → Result Win.
- Player Army defeated → Result Lose.
This answers:
- "what if the player does not match?" — there is no puzzle during Battle.
- "what if the player does not cast?" — Battle continues and the player may lose an intervention opportunity.
## Battle Setup Requirement
Before combat starts:
- resolve Beast Queue through STAR-001,
- show unit role + star,
- provide a small battlefield slot layout,
- allow drag/click placement or slot assignment,
- show Energy Queue / charges available for the coming Battle,
- Start Battle only after a valid arrangement.
For the first slice, units may be locked after Start Battle. Mid-combat reposition is an Open Decision.
## P1 Slice Order
### P1-S0 — State Migration
- preserve P0 code and checks where reusable,
- add BeastRush / EnergyRush / BattleSetup / Battle / Result flow,
- no combat depth yet.
### P1-S1 — Energy Pre-Collection
- move Energy board before Battle,
- create EnergyQueue,
- remove active-Battle puzzle dependency,
- verify queued Energy survives into BattleSetup/Battle.
### P1-S2 — Beast Role + Arrangement
- expose role labels,
- convert queue through STAR-001,
- create simple battle slots,
- allow arrangement before Start Battle.
### P1-S3 — Autonomous Battle
- add minimal Player Army HP/DPS and Enemy HP/DPS/tick model,
- Battle progresses with zero player input,
- Win/Lose both possible.
### P1-S4 — Timed Energy Cast
- consume stored Energy charge during Battle,
- implement one timing-sensitive skill,
- verify no-cast path still progresses,
- verify cast timing can change outcome/state.
### P1-S5 — Validation Instrumentation
Add only metrics needed for the structural questions.
Candidate metrics:
- beastMatches
- energyMatches
- beastQueueAtSetup
- energyChargesAtBattleStart
- roleCounts
- starTierCounts
- arrangementChanges
- timeInBattleSetup
- firstCastTime
- castsUsed
- unusedChargesAtResult
- battleDuration
- resultWinLose
- armyHpAtFirstCast / enemyHpAtFirstCast
## Regression Requirements
Keep reusable P0 checks for:
- Onet pathing,
- board generation,
- deadlock recovery,
- STAR-001 conversion.
Retire or rewrite P0 checks that assume:
- Energy puzzle exists during active Battle,
- Energy gauge +10 / max20 is the active P1 rule,
- Battle cannot progress without player Energy matching.
## Anti-Scope-Creep
Do not add:
- full Unity navigation/targeting,
- multiple waves,
- equipment,
- meta progression,
- multiple battlefield maps,
- more than one Energy skill before timing value is proven,
- mid-combat reposition unless later evidence requires it,
- polished art.
## P1 Exit Gate
P1 structural prototype is ready for playtest when:
- [ ] Beast Rush fills Beast Queue.
- [ ] Energy Rush fills Energy Queue.
- [ ] Both queues persist into Battle Setup.
- [ ] STAR-001 converts Beast output.
- [ ] Player can arrange role-readable Beast units.
- [ ] Battle advances with no player input.
- [ ] Battle can reach Win/Lose without Energy cast.
- [ ] Stored Energy can be cast at a chosen moment.
- [ ] One Energy skill has visible timing value.
- [ ] Result records P1 validation metrics.
- [ ] Production build passes.
- [ ] Full live browser flow passes.
## Source-of-Truth Rule
If implementation conflicts with the Current Gameplay Spec, stop and report the mismatch. Do not silently preserve the P0 behavior because it already exists.
